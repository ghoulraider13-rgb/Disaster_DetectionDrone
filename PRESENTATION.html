Project Presentation 1 / 14

The Problem: The Golden Hour

During disaster response, the first hours decide who survives.

🚫 Inaccessible Terrain

Floodwater, debris, unstable slopes block ground teams from reaching victims.

📡 Bandwidth Failure

Cell towers down; streaming video to operators impossible in disaster zones.

⏱️ Time Critical

Survival probability drops ~10% per hour for trapped victims (FEMA data).

Current gap: Drones exist, but lack onboard intelligence to detect survivors, flood extent, landslides, or structural damage autonomously.
The Problem 2 / 14

Solution: Onboard AI for SAR Drones

Compact YOLOv11 models running directly on drone companion computers — no cloud, no streaming, real-time detection.

Three Specialized Models

  • Flood: Extent mapping + survivor detection
  • Landslide: Slope failure & debris flow detection
  • Earthquake: Rubble & structural damage assessment

Key Capabilities

  • 1280×1280 resolution for small aerial objects
  • ~11M params (YOLOv11s) — fits Jetson Orin Nano
  • Export to ONNX, TensorRT, OpenVINO, TorchScript
  • CLI-first for fleet training & CI/CD

Deployment Flow

Train (GPU) → Export (ONNX)
    → TensorRT (on Jetson)
    → Deploy (drone_detect.inference)
    → Real-time ≥30 FPS @ 1280²

Datasets (Pinned Roboflow)

  • Flood: Hurricane Harvey aerial (v2)
  • Landslide: UAV slope failures (v1)
  • Earthquake: Post-quake rubble (v1)

Reproducibility Mechanisms

🔒 Pinned Versions

Exact dataset version in YAML config; bump only when intentional.

🎲 Fixed Seed

seed=42 + deterministic=True — identical results every run.

⏹️ Early Stopping

patience=30 on val mAP — stops at convergence, not fixed epochs.

📦 Config-Driven

All hyperparameters in configs/datasets.yaml, zero hardcoded values.

CLI-First Workflow

Everything scriptable for CI/CD, fleet training, and automated deployment.

📋 Dataset Management

# List all configured datasets
drone_detect datasets list

# Download all (or one)
drone_detect datasets download
drone_detect datasets download --only flood

🚀 Training

# Train all three models
drone_detect train

# Single model with overrides
drone_detect train --only landslide \
  --epochs 100 --device cpu

# Override base model
drone_detect train --only earthquake \
  --model yolo11n.pt

📦 Export for Edge

# ONNX (general)
drone_detect export \
  --weights runs/drone_models/flood_model_v2/weights/best.pt \
  --format onnx

# TensorRT (Jetson)
drone_detect export --format engine

# OpenVINO (Intel)
drone_detect export --format openvino

🔍 Inference

# Image
drone_detect predict --weights best.pt \
  --source image.jpg --conf 0.25

# Video (annotated output)
drone_detect predict --weights best.pt \
  --source video.mp4 --conf 0.25

# Webcam / RTSP
drone_detect predict --weights best.pt --source 0

Export Formats for Edge Deployment

Choose the right format for your target hardware.

Format Target Hardware Latency Complexity Best For
ONNX ONNX Runtime (CPU/GPU) Medium Low Validation, cross-platform
TensorRT (engine) NVIDIA Jetson Orin/Nano Lowest Medium (build on target) Production drone payloads
OpenVINO Intel CPU/VPU/NPU Low Low Intel-based edge boxes
TorchScript Python-only High Lowest Rapid prototyping, no C++
Recommended production path: best.pt → ONNX → (on Jetson) trtexec → best.engine → drone_detect.inference

Target: ≥30 FPS @ 1280×1280 on Jetson Orin Nano

Export CLI Options

drone_detect export \
  --weights runs/drone_models/flood_model_v2/weights/best.pt \
  --format engine \          # onnx | engine | openvino | torchscript
  --output-dir ./deploy/     # optional destination

Kaggle/Colab Notebook

Interactive end-to-end walkthrough: download → train → visualize — runs as-is on free GPUs.

Features

  • No hardcoded credentials — reads ROBOFLOW_API_KEY from secrets
  • Single loop trains all three models (no copy-paste)
  • Correct output paths from Ultralytics save_dir
  • Visualizes confusion matrix, curves, val predictions
  • Sanity-check inference with test-time augmentation

Notebook Structure

  1. Install dependencies (pinned versions)
  2. Configure datasets (mirrors configs/datasets.yaml)
  3. Download + train all models in loop
  4. Visualize each run's artifacts
  5. Sanity-check inference on validation image

Key Code Snippet

rf = Roboflow(api_key=API_KEY)
for name, cfg in DATASETS.items():
    dataset = rf.workspace(WORKSPACE) \
        .project(cfg["project"]) \
        .version(cfg["version"]) \
        .download(model_format="yolov11")

    model = YOLO("yolo11s.pt")
    results = model.train(
        data=str(Path(dataset.location) / "data.yaml"),
        project="runs/drone_models",
        name=cfg["run_name"],
        **TRAIN_ARGS,
    )
    run_dirs[name] = Path(results.save_dir)

Known Issues & Limitations

Transparent about current gaps — fixes tracked in roadmap.

🔴 Critical

  • Missing best.pt — Flood training run exists but weights not produced. Likely interrupted or path bug.
  • Nested run dir — Output at runs/detect/runs/drone_models/ instead of runs/drone_models/. Fix in train.py project/name handling.

🟡 Medium

  • No weights in repo — Distributed via Releases only (by design, but docs should clarify).
  • Single-class datasets — Current Roboflow data may have only 1–2 classes; real SAR needs more.
  • RGB-only — No thermal modality; night ops need fusion (P1 roadmap).

🟢 Minor

  • Tests only cover config loading (no integration tests)
  • No CONTRIBUTING.md or issue templates
  • No automated release workflow
  • Notebook could add metric logging to Weights & Biases / MLflow

📋 Design Choices

  • YOLOv11s over nano — paper shows <1–2 mAP gain worth the latency
  • 1280² resolution — small objects (survivors) need it
  • CLI-first — notebook is convenience, not interface
  • AdamW + cosine — better fine-tuning than SGD defaults
